# 自己建文件／資料庫問答（RAG），接進「查詢」分頁

DHC CLI 的「查詢」分頁本身沒有檢索功能。它只是列出 `<workspaceRoot>\內部資料查詢\<專區名>\` 底下的每個專案資料夾，每個專案用一份 `CLAUDE.md` 告訴 AI Agent 該怎麼回答。檢索、嵌入、作答這些能力要你自己準備，再讓 `CLAUDE.md` 指向它們。

## 1. 什麼時候需要 RAG

先問資料量，再決定要不要建：

| 情況 | 建議 |
|---|---|
| 文件加起來一兩百頁以內，格式單純（md、txt、docx、pdf 有文字層） | 不用 RAG。把檔案放進專區資料夾，讓 AI 直接讀檔、用 grep 找就夠。 |
| 文件幾百頁到幾千頁，問題常跨多份文件 | 建 RAG。 |
| 資料在資料庫，問題是「某天某欄位是多少」 | 通常不是 RAG，而是寫好唯讀的查詢腳本，AI 呼叫腳本取數字。 |
| 內容常更新 | 能用 grep 就先用 grep；要建索引就要設計重建流程。 |

RAG 會多出索引維護、版本同步、檢索品質這幾項成本。AI 直接讀得完就不要建。

## 2. 切段（chunking）

- 依結構切，不要只依字數切。法規、規章、合約依「條」「項」切；手冊、SOP 依標題層級切；表格整張或整列群組保留，不要切在列中間。
- 每段都存來源資訊：檔案路徑（相對於專區資料夾）、頁碼或段落編號、所屬標題路徑。之後的引用全靠這些欄位。
- 大小：一段約 300 到 800 個中文字；超過就在句子邊界再切。相鄰段落重疊 10% 到 15%，避免答案正好被切斷。
- 在每段開頭補上標題路徑（例如「第三章 > 3.2 申請流程」），檢索時能帶到上下文。
- 保留文件版本或修訂日期。同一份規章有新舊版時，索引要能分辨。

一筆 chunk 的欄位示意：

```json
{
  "id": "doc-a#p12#s3",
  "source": "規章/doc-a.pdf",
  "page": 12,
  "section": "第三章 > 3.2 申請流程",
  "text": "……"
}
```

## 3. 嵌入（embedding）

| 選項 | 優點 | 缺點 |
|---|---|---|
| 本地模型（例如開源的多語嵌入模型，用本機推論服務跑） | 資料不出機器；沒有按量費用 | 要自己維護；速度與中文品質取決於模型和硬體 |
| 雲端嵌入 API | 品質穩、免維護 | 文字會送到服務商；要評估資料分級與合約 |

資料屬於機敏或受規範的，選本地模型。只用公開或已去識別資料，才考慮雲端。建索引和查詢時必須用同一個嵌入模型與版本，換模型就要整批重建。

## 4. 檢索

- 混合檢索：向量相似度加關鍵字（BM25 或全文檢索）。向量擅長語意，關鍵字擅長條號、代碼、專有名詞，兩者互補。
- 兩路各取前 20 到 50 筆，用 reciprocal rank fusion 之類的簡單方式合併。
- top-k：交給作答模型的段落通常 5 到 10 段。太少會漏，太多會稀釋。
- 重排序（rerank）：合併後用 cross-encoder 或模型對「問題＋段落」重新打分，再取前幾名。沒有重排序模型時，先把混合檢索做好，再決定要不要加。
- 檢索腳本回傳的內容至少要有：段落文字、來源路徑、頁碼或段落編號、分數。

## 5. 作答

- 作答模型可以是本地或雲端，取捨同嵌入：資料能不能離開機器。
- 提示詞要求：只根據提供的段落作答；段落沒有答案就明說「文件中找不到」；不補充段落以外的常識或推測。
- 一次回答一個問題；跨文件比較時，每份文件的結論分開寫。
- 檢索分數都很低時，直接回「找不到」，不要硬答。

## 6. 附出處與逐字核對

每個論點都附「檔名＋段落」。更進一步，要求模型把引用的原文句子逐字貼出，再用程式核對：

1. 從回答中抽出所有引用句與其來源。
2. 到原文（不是 chunk 摘要）裡找這句話，先做空白與全半形標準化。
3. 找得到：標示通過。找不到或只有部分相符：標紅，並提示「引用無法在原文找到，請人工確認」。

這一步不靠模型判斷，只靠字串比對，成本低，卻能抓到編造的引用。標紅的回答不要當結論使用。

最小的核對邏輯示意（Node.js）：

```js
const norm = (s) => s.normalize('NFKC').replace(/\s+/g, '');
export const quoteExists = (quote, sourceText) =>
  norm(sourceText).includes(norm(quote));
```

## 7. 只讀權限

- 資料庫用唯讀帳號，且只開放必要的表或檢視。連線字串不要寫進 `CLAUDE.md`，放在腳本讀取的環境變數。
- 文件資料夾以只讀方式提供；索引檔放在獨立位置。
- 不給 AI 寫入、刪除、執行任意指令的工具。專區專案的 `CLAUDE.md` 明寫禁止事項，並用 Agent 的權限設定把工具限縮到「執行檢索腳本」與「讀檔」。
- 腳本層也要擋：查詢腳本只接受 SELECT，或只呼叫預先寫好的參數化查詢。

## 8. 接進 DHC CLI

本機腳本統一用 Node.js（`.mjs`），和 repo 其他工具一致。建議結構：

```
<workspaceRoot>\內部資料查詢\<專區名>\
  CLAUDE.md          # 告訴 AI 怎麼答
  search.mjs         # 檢索腳本：輸入問題，輸出 JSON 段落
  verify.mjs         # 逐字核對腳本
  index\             # 索引檔
```

`CLAUDE.md` 範例：

```markdown
# <專區名> 問答

你是唯讀的資料查詢助理，只回答 <資料範圍> 相關的問題。

## 流程
1. 收到問題後，先執行 `node search.mjs "<問題>"`，取得最相關的段落（JSON，含檔名、頁碼、段落編號、原文）。
2. 只根據這些段落作答。段落沒有答案時回答「文件中找不到」，不要用常識補。
3. 每個論點後面附出處：`（檔名，第 N 頁／第 N 條）`，並貼出引用的原文句子。
4. 回答完成後，執行 `node verify.mjs` 核對引用句。核對不過的句子標紅，並說明無法確認。

## 不能做
- 不修改、刪除、新增任何檔案或資料。
- 不執行 search.mjs 與 verify.mjs 以外的指令。
- 不輸出個人識別資訊與帳號密碼。
- 不推測未在文件中出現的數字或日期。
```

## 9. 驗收

上線前準備 20 到 40 題有標準答案的題庫，題型要涵蓋：

- 單一文件、單一段落可答的直接題
- 需要跨段或跨文件的整合題
- 文件裡沒有答案的題目（預期回答「找不到」）
- 條號、代碼、數字等精確比對題

量兩個數字：

- 答對率：回答與標準答案一致的比例。
- 錯誤引用率：引用句在逐字核對時失敗的比例。

兩個數字要分開看。答對但引用錯，仍然不可信。改了切段、嵌入模型或提示詞之後，重跑同一份題庫，確認沒有退步再上線。題庫也要定期補新題，尤其是曾經答錯的題目。
